# PRN Order Viewer — 임상적 유용성 검토 및 개발 우선순위

> 결정일: 2026-10-10 | 기준 코드: v0.5 (`3e03d5304157e2faf741e60f680ae408efe2ed45`)
> 상태: 사용자 동의에 따라 **개발 방향으로 채택**. 임상적 효과와 개별 UI 구현은 아직 검증/확정되지 않음.

## 1. 합의된 목표와 임상적 가치 판단

- 출발점은 **간호대학생의 실습 경험에서 제기된 PRN 처방 탐색·확인 불편**이다. 실제 병원 EMR에 특정 기능이 없거나 성능이 열등하다는 사실은 확인되지 않았다.
- PRN 전용 조회는 유용할 **가능성**이 있으나, 기존 EMR 기능과 중복될 수 있고 임상적인 효과는 아직 입증되지 않았다. PRN 탭 자체를 목적이나 성과로 취급하지 않는다.
- 당장은 **PRN 처방 확인에 직접 도움을 주는 기능**(탐색, 주요 지시의 이해, 현재 상태·변경사항의 구별)에 집중한다.
- 장기 목표는 병원 업무 개선에 도움이 되는 통합형 EMR을 검토하는 것이지만, 현 단계는 **독립형 가상 환자·가상 처방 프로토타입**이다.
- 처방 조회·열람 확인·의사 처방·실제 투약 수행·간호기록은 서로 다른 이벤트이며, '유효(active)'는 **현재 투약 가능**을 뜻하지 않는다.

## 2. 기능 채택 기준 — 신규 개발 전에 반드시 검토

1. 어떤 **PRN 확인 업무의 문제**를 해결하는지 구체적 시나리오로 정의한다.
2. 이미 구현된 기능 또는 실제 현장에서 사용 중인 도구와 **중복될 가능성**을 평가한다. 실제 EMR 기능을 확인할 수 없으면 '미확인'으로 기록한다.
3. 정보 탐색시간 감소, 처방 선택 오류 감소, 최신 지시 인지, 화면 이동 감소 등 **관찰 가능한 기대효과**를 하나 이상 정한다. 효과가 입증되었다고 미리 쓰지 않는다.
4. 추가 클릭·확인 부담, 알림 피로, 데이터 불일치, 오래된 처방 복제, 버전 혼동 등 **역효과**를 평가한다.
5. 기존 데이터·환자 분리·PRN/STAT 구분·처방 버전·간호사 확인 이력·MICU 읽기 전용 연동에 미치는 영향을 확인한다.
6. 직접적인 PRN 확인 가치가 없거나 증거가 부족한 기능은 **지금 구현하지 않고 조사 후보로 보류**한다.
7. 중요한 업무 흐름·UI·자료 보존/삭제·모듈 통합은 대안을 제시한 뒤 사용자 결정에 따른다.

## 3. PRN 개발 우선순위 (기능 확정과 후보를 구분)

| 구분 | 후보 작업 | 판단 및 범위 |
|---|---|---|
| P0: 기존 보호·검증 | 현재 PRN 검색/상태 필터/원문/처방 버전/간호사 열람 기록·v0.5 구조화 입력 회귀검증 | **필수 작업**. 실제 Node.js 및 브라우저 통합 테스트 미완료 상태를 해소. 코드의 임상적 정확성까지 검증되었다고 주장하지 않음 |
| P1: 현재 PRN 확인 개선 | 적응증·투여 조건·용량·경로·빈도·간격·처방 상태를 명확히 확인 | **우선 검토**. 필요한 정보가 한 번에 식별되는지 가상 시나리오에서 확인 |
| P1: 현재/이전 지시 분리 | 변경·보류·중지 전후 차이, 현재 버전, 오래된 구조화 필드(stale) 강조 | **우선 검토**. 현행 버전별 이력 유지하고 실제 사용성은 별도 검증 |
| P2: 비교 시나리오 | 동일/유사 적응증 PRN 간 조건·경로·지시 차이 비교 | **기능 후보**. 약물 우선순위나 투약 추천은 하지 않음; 효용 검증 후 채택 결정 |
| P2: 간호사 열람 확인 | 현행 시뮬레이션 유지. 별도 확인 행위의 실제 필요성·중복 업무 부담 평가 | **유지하되 확장 보류**. 기관별 업무 규칙을 보편적 기준이라 주장하지 않음 |
| P3: 후속 별도 검토 | 최근 실제 투약 시각, 투약 수행·효과 재평가/기록 연계 | **PRN MVP 범위 밖**. 신뢰할 수 있는 투약 수행 데이터와 기관 승인·업무 근거 확보 이후 검토 |
| P3: 장기 별도 검토 | 자동 투약 가능 판단, 간격/최대량 계산, 임상경고/추천 | **현재 금지**. 임상적 검증·전문가 검토·기관별 정책 없이는 구현하지 않음 |

**이 표는 기능 구현 승인 목록이 아님.** P1/P2의 구체적 UI 변경은 기존 기능 확인·위험 검토·사용자 결정 이후 진행한다. 이번 결정으로 확정된 것은 우선순위 원칙이다.

## 4. 가상 환경에서의 검증 계획

- 과제 A: 정규·PRN 혼합 환자에서 지정 PRN 찾기 및 관련 지시 정확히 식별.
- 과제 B: 같은 적응증의 서로 다른 가상 PRN 처방 구별(해당 사례가 있는 경우).
- 과제 C: 보류·중지·변경된 처방의 현재 지시와 과거 지시 정확히 구분.
- 지표: 과제 완료시간, 정확도/오선택, 최신 변경사항 인지율, 화면 이동/클릭 수, 주관적 혼란 및 추가 업무 여부.
- 대조: 가능하면 **같은 가상 데이터**로 기존 표시 방식과 개선안을 비교한다. 실제 병원 EMR과 비교했다고 쓰려면 해당 환경의 정당한 비교자료가 필요하다.
- 단계: 소규모 내부 시나리오 → 가능한 범위의 간호사·약사 의견 → 적절한 기관 절차를 준수한 실제 업무 요구 검토.
- 현재 기준값, 최소 개선폭, 사용성 합격선은 **미설정**. 실측 또는 이해관계자 협의 없이 숫자를 임의 확정하지 않는다.
- 소규모 시뮬레이션 결과를 실제 투약오류 감소나 환자안전 개선의 인과적 입증으로 해석하지 않는다.

## 5. 장기 통합 시스템에 대한 결정

- **환자 중심**의 공통 업무 맥락을 장기적으로 지향한다. PRN 프로젝트를 중심 *개발 애플리케이션*으로 활용할 수 있어도, 모든 EMR 기능을 PRN 데이터 모델 아래 통합하는 것은 아니다.
- 간호처방 UI/UX 개선과는 환자·처방 참조·간호 수행의 연계를 필요성이 확인된 뒤 검토한다. 저장소·DB 및 정상 동작을 보호한다.
- MICU 화재대피 인원배치와는 직원·근무 정보의 최소 단위 연동 가능성만 보며, 관련성이 부족하면 독립 프로젝트로 유지한다. 근무자 정보가 실제 로그인·처방 열람 확인자를 인증하지 않는다.
- 검사·간호진단·간호기록 등 범위 확장은 PRN MVP의 필요 기능과 사용성 검증 이후에 별도 결정한다.

## 6. 변경 금지선 및 미결정 사항

- 기존 가상 환자 4명·처방 18건·약물 후보 107종을 임의 수정·임상 데이터로 보강하지 않는다.
- 미검증 제형·함량·용량을 107개 약물 전체에 일괄 입력하지 않는다.
- 기존 자유문장 호환·PRN/STAT 구분·처방 ID/버전별 확인 이력·MICU 읽기 전용 기능을 보호한다.
- 실제 환자/직원 정보 및 승인받지 않은 병원 내부자료를 입력·업로드하지 않는다.
- 저장 정책은 **미확정**: IndexedDB 영구 저장, 자동 삭제, JSON 백업·복원, 데이터 마이그레이션을 임의 도입하지 않는다.
- 실제 투약 가능 여부, 승인·전자서명, 임상 의사결정 기능은 개발 범위에 포함하지 않는다.
- 현재 UI는 잠정안이며, 장기 통합·핵심 업무 흐름·중요 UX 변경은 사용자 승인 후 정한다.

## 7. 다음 개발 세션의 시작 순서

1. GitHub `main` 최신 상태·코드·문서·기존 테스트 확인.
2. `P0`의 미완료 Node.js/브라우저 회귀검증과 구조화 입력·변경 후 stale 표시에 대한 점검.
3. PRN 확인 과제를 명확히 정의하고 `P1` 후보의 예상 이점·위험·대안 제시.
4. 사용자 결정이 필요한 UI/업무 변경은 제안 후 승인; 그 외 내부 변경은 작은 패치로 진행.
5. 신규 기능 검증·영향받는 기존 기능 회귀검증, 문서 업데이트, GitHub 원격 커밋 확인.
