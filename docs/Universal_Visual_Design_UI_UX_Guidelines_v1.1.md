> **상태:** 범용 가이드 개정 초안(DRAFT) — 2026-10-15  
> **출처:** `Universal Visual Design & UI/UX Guidelines v1.0`의 개선판. 원형은 `Educational Simulator UI/UX Design Standard v1.0`  
> **적용 범위:** 웹사이트, 개인 블로그·콘텐츠 플랫폼, 웹·모바일 앱, 대시보드, 교육 서비스, 정보 시각화, 디지털 문서·프레젠테이션  
> **적용 효과:** 앞으로의 설계 및 리뷰에 쓰는 판단 기준이다. 이 문서 자체는 기존 화면·코드·브랜딩·상태 동작을 변경하거나 승인하지 않는다.

## 0. 사용 방법과 규범 수준

이 문서는 특정 서비스의 화면을 복제하기 위한 스타일 키트가 아니라 **좋은 시각적 결정과 상호작용을 반복 가능하게 만드는 설계 기준**이다. 콘텐츠 성격, 이용자, 브랜드, 기기, 접근성 요구가 다르면 최종 표현도 달라질 수 있다.

- **MUST — 필수:** 명확성, 정직성, 접근성, 안전 및 기존 계약과 관련된 기본 원칙. 예외가 필요하면 사유를 기록한다.
- **SHOULD — 권장:** 일반적으로 유리하지만 목적과 실증적 근거에 따라 조정할 수 있는 패턴.
- **MAY — 선택:** 프로젝트 특성에 맞춰 쓰는 예시·표현 방식·토큰 값.
- **참고 ≠ 복제:** 다른 브랜드의 로고, 고유 그래픽, 제품 외관, 화면 구조를 그대로 복사하지 않는다. 원리와 효과를 분석하여 새 맥락에 재설계한다.
- **프로젝트별 계약 우선:** 기존 서비스에 적용할 때는 해당 프로젝트의 승인된 UX, 디자인 토큰, 데이터·기능·안전 요구가 우선한다. 충돌이 발생하면 비교·제안 후 승인받는다.
- **검증의 증거 수준:** 문서상의 원칙 준수, 정적 검사, 자동 실행 테스트, 실제 브라우저·기기 테스트, 사람 대상 사용성 검증은 서로 다른 근거다. 수행하지 않은 검증을 완료했다고 표시하지 않는다.
- **작업 비례성:** 적용되는 MUST는 지키되 검토·테스트의 범위는 변경 위험에 비례하도록 조절한다. 단순한 시각 변경을 무조건 전체 시스템 재검증으로 확대하지 않으며, 데이터·안전·핵심 상태의 변경은 축소 검증하지 않는다.

**한 문장 목표:** 사용자가 화면이나 콘텐츠를 처음 보았을 때 *무엇인지, 무엇이 중요한지, 무엇을 할 수 있는지, 무엇이 달라졌는지*를 어렵지 않게 이해하도록 만든다.

## 1. 디자인 철학: Less, but better

디자인을 장식이 아닌 **의미·구조·조작·신뢰의 설계**로 본다. 아래는 디터 람스의 좋은 디자인 10원칙을 디지털 매체에 적용하기 위한 **본 문서의 해석**이며, 원칙의 공식 원문을 대체하는 번역이 아니다.

| 디터 람스의 원칙 | 디지털 시각 디자인으로의 해석 |
|---|---|
| 혁신적(Innovative) | 새 기술·형식은 실제 문제를 해결할 때만 도입한다. |
| 유용함(Useful) | 사용자의 목적 달성과 이해를 시각적 유행보다 우선한다. |
| 심미적(Aesthetic) | 정렬·비례·대비·완성도를 통해 편안하고 정돈된 인상을 준다. |
| 이해 가능(Understandable) | 구조와 작동 방식이 설명 없이도 가능한 한 드러나게 한다. |
| 절제(Unobtrusive) | 콘텐츠와 사용자의 작업을 인터페이스가 방해하지 않는다. |
| 정직함(Honest) | 성능·데이터·효과·상태를 과장하거나 오인시키지 않는다. |
| 오래 지속됨(Long-lasting) | 일시적 유행보다 수정·확장·유지가 쉬운 체계를 선택한다. |
| 세부까지 철저함(Thorough) | 간격, 정렬, 오류·빈 상태, 작은 화면까지 일관되게 설계한다. |
| 환경을 배려함(Environmentally friendly) | 불필요한 자산·자동재생·무거운 효과·잦은 교체를 줄인다. |
| 가능한 한 최소한의 디자인(As little as possible) | 꼭 필요한 요소를 남기되 중요한 정보를 숨기지는 않는다. |

**MUST:** 단순해 보이게 만들기 위해 중요한 콘텐츠·경고·출처·기능·조작 가능성을 희생하지 않는다. 정보의 양이 많다면 삭제 전에 **분류, 그룹화, 위계, 단계적 공개**를 검토한다.

## 2. 디자인 레퍼런스: 철학과 실제 구현을 모두 본다

각 레퍼런스의 **원칙 / 관찰 대상 / 적용 상황 / 주의점**을 구분한다. 여러 시스템을 통째로 섞지 말고, 해결하려는 문제와 맞는 패턴만 선택한다.

### 2.1 Dieter Rams / Braun — 철학과 실제 제품 디자인

실제 제품의 형태와 조작 구조를 분석하되, 물리 제품의 형태를 디지털 화면에 억지로 재현하지 않는다.

| 실제 제품 | 살펴볼 관찰 지점 | 디지털 인터페이스에 적용하는 예 |
|---|---|---|
| **Braun T3 Pocket Radio (1958)** | 반복적인 격자, 간결한 조작부, 정렬과 여백, 요소 간 비례 | 도구 모음, 간결한 정보 카드, 작은 화면의 균형 있는 정보 배치 |
| **Braun ET66 Calculator** | 버튼 그룹, 숫자·기능 구분, 제한된 강조색, 즉각적 조작 이해 | 계산기·설정 패널·폼·툴바의 중요도 구분 및 상태 설계 |
| **Braun SK4 (1956; Hans Gugelot와 공동 작업)** | 구조의 가시성, 재료와 요소의 분리, 조작부 배치 | 콘텐츠와 조작부의 역할 분리, 숨기지 않는 상태 및 정보 구조 |
| **Braun T1000 World Receiver (1963)** | 복잡한 기능을 질서 있게 정리한 패널, 정교한 눈금·라벨·계층 | 분석 대시보드, 고밀도 데이터 화면, 고급 설정 패널 |

**주의:** ET66은 람스가 총괄한 Braun 디자인 계보에서 Dietrich Lubs 등과의 작업 맥락을 함께 살펴야 하며, 제품별 기여를 람스 개인의 단독 작업으로 단정하지 않는다. SK4는 Hans Gugelot와 공동 디자인이다. 작품의 사진·도면은 저작권과 사용 조건을 별도로 확인한다.

**레퍼런스 분석 질문:** (1) 무엇이 먼저 보이는가? (2) 정렬·비례는 어떤 규칙을 가지는가? (3) 강조색은 왜 그곳에만 쓰였는가? (4) 조작 가능한 요소를 어떻게 알아보는가? (5) 이 원칙이 내 제품의 목적에도 실제로 유효한가?

### 2.2 ChatGPT 인터페이스 — 집중과 읽기 경험

- **관찰 대상:** 여백을 활용한 집중, 명확한 주 진입점, 내용 중심의 읽기 폭, 입력·행동의 구분, 낮은 시각적 잡음.
- **적용 예:** 블로그의 본문 읽기 영역, 검색·입력 중심의 도구, 장문의 분석 페이지, 복잡한 도움말.
- **주의:** 채팅형 레이아웃이 모든 제품의 정답은 아니다. ChatGPT의 현재 인터페이스는 변화할 수 있으므로 이 문서는 **특정 시점의 픽셀·브랜딩이 아니라 관찰 가능한 패턴**만 참조한다.

### 2.3 Apple Human Interface Guidelines — 목적과 상호작용의 품질

- **관찰 대상:** 목적·사용자 주도권·책임·친숙함·유연성·간결함·디테일·만족감, 내비게이션, 의미 있는 피드백과 움직임.
- **적용 예:** 화면 전환, 입력 후 결과, 되돌리기·취소, 플랫폼별 적응형 UI.
- **주의:** Apple 플랫폼 전용 API·시각 효과를 웹이나 다른 운영체제에 무조건 강제하지 않는다.

### 2.4 보완 디자인 시스템 — 상황별로 골라 사용

| 체계 | 활용 상황 | 핵심 참고 항목 |
|---|---|---|
| **KRDS** | 공공성 높은 서비스·한국어 폼 | 레이블, 오류, 입력, 접근성, 상태 전달 |
| **NHS Design System** | 건강·의료·복잡한 안내 | 쉬운 용어, 서비스 흐름, 안전 관련 정보의 명확성 |
| **IBM Carbon** | 데이터·업무용 대시보드 | 디자인 토큰, 표, 시각화, 복합적인 상태·색상 구조 |
| **WCAG 2.2** | 웹 접근성 검수 전반 | 인지·조작·이해·호환성의 평가 기준 |

**MUST:** 레퍼런스를 채택할 때 “어디서 가져왔는가”보다 “무슨 문제를 해결하려는가”를 명시한다. 서로 충돌하는 패턴을 무비판적으로 혼합하지 않는다.

## 3. 범용 디자인 핵심 원칙 (MUST)

1. **목적의 명료성:** 주요 화면·문서마다 주제, 대상, 핵심 가치 또는 주요 행동을 빠르게 이해할 수 있어야 한다.
2. **정보 위계:** 중요도에 따라 크기·위치·굵기·여백·색상을 차등 적용한다. 모든 요소가 똑같이 강조되면 아무것도 강조되지 않는다.
3. **일관성과 예측 가능성:** 같은 역할의 요소는 같은 방식으로 보이고 작동한다. 차이가 있다면 이유가 있어야 한다.
4. **내용 중심:** 장식은 메시지를 돕는 범위에서 사용한다. 정보가 많은 페이지는 콘텐츠를 잘 조직해야지, 일괄적으로 숨기거나 삭제해서는 안 된다.
5. **정직한 표현:** 사실·가정·예시·데모·AI 생성물·광고/협찬·의견·불확실성을 필요한 범위에서 구분한다.
6. **접근성:** 읽기, 이해, 키보드 조작, 초점 인식, 확대, 색각 다양성, 움직임 감소 등을 초기 설계부터 고려한다.
7. **맥락에 맞는 밀도:** 소개 페이지는 여유를, 전문 대시보드는 정보 간 연결을 중시한다. 모든 화면에 동일한 카드 수나 여백을 강요하지 않는다.
8. **피드백과 복구:** 상호작용이 있으면 결과, 진행 상태, 오류, 복구 방법을 명확히 알려야 한다.
9. **반응형 적응:** 화면이 작아져도 의미·읽기 순서·주요 기능은 유지한다. 무리한 축소보다 재배치·확대·부분 스크롤을 선택한다.
10. **검증 가능한 선택:** 좋은 디자인이라는 평가는 외형의 취향뿐 아니라 과제 성공, 이해도, 읽기 편의성, 오류, 만족도 등으로 확인한다.
11. **맥락에 맞는 표현적 정체성:** 시각적 절제는 브랜드·콘텐츠의 개성을 제거하라는 뜻이 아니다. 목적에 부합하는 색채·이미지·레이아웃·모션을 적극 활용할 수 있으며, 그 표현이 정보의 이해·접근성·사용성을 해치지 않도록 한다.

## 4. 시각 언어: 실제 설계 기준

이 장의 수치와 패턴은 범용 시작점이다. 브랜드·콘텐츠·기기별로 조정하되 사용성 및 접근성 요건을 먼저 확인한다.

### 4.1 레이아웃과 여백

- **SHOULD:** 정렬 기준, 컨테이너 폭, 열 사이 간격을 먼저 정하고 그 안에 요소를 배치한다. ‘그냥 예뻐 보이는 위치’보다 반복되는 규칙을 우선한다.
- **SHOULD:** 텍스트 위주 페이지에서는 한 줄이 지나치게 길어지지 않게 한다. 본문 폭 **약 60~75ch**는 라틴 문자 중심 콘텐츠에서 참고할 수 있는 초기 범위일 뿐, 한국어에 그대로 적용할 고정 기준은 아니다. 실제 서체·한영 혼용·화면 폭에서 검증한다.
- **SHOULD:** 공백을 빈 공간이 아니라 **요소 사이의 관계**를 표현하는 수단으로 쓴다. 같은 그룹 안보다 다른 그룹 사이의 간격을 더 크게 둘 수 있다.
- **SHOULD:** 카드·구분선·배경 음영을 동시에 중첩하는 습관을 피한다. 하나의 구획 방식만으로 충분한지 먼저 확인한다.
- **MAY:** 기본 간격 토큰 예시: `4 / 8 / 12 / 16 / 24 / 32 / 48 / 64px` (불변 규정 아님).
- **MUST:** 관련 내용을 함께 봐야 이해되는 경우에는 동시에 보여준다. 시각적 간결함을 위해 인과관계나 비교를 해체하지 않는다.
- **SHOULD:** 브랜드·문화·서사 콘텐츠의 시각적 개성이 중요한 프로젝트에서는 정돈된 기본 구조 위에 고유한 편집 레이아웃·일러스트·색채를 허용한다. 단, 강조 요소는 목적을 가져야 하며 접근성을 유지해야 한다.

### 4.2 타이포그래피

- **SHOULD:** 디지털 장문 본문은 **약 16px 이상**, 보조 설명은 가급적 **14px 이상**에서 검토한다. 이는 프로젝트 권장 목표이지 모든 매체의 법적 최소 규격이 아니다.
- **SHOULD:** 장문 행간은 **약 1.5~1.7**을 출발점으로 하고, 제목·표·버튼·그래프 라벨은 용도에 맞춰 별도로 조정한다.
- **SHOULD — 한국어 장문:** `ch` 단위만으로 가독성을 판정하지 않는다. 한글·영문·숫자 혼합 비율, 실제 화면의 한 줄 길이, 조사·단어 단위 줄바꿈, 문단 간 간격, 글꼴의 자소 가독성을 확인한다. 데스크톱과 320~390px 화면에서 샘플 **본문·인용문·표·참고문헌**을 실제 내용으로 시험한다.
- **SHOULD — 다국어:** 여러 언어가 혼합되는 경우 줄바꿈과 긴 링크/DOI의 넘침, 글꼴 대체 및 숫자·단위 표기를 함께 확인한다.
- **SHOULD:** 역할 기반 타입 토큰을 정의한다: `display / heading-1 / heading-2 / heading-3 / body / body-strong / caption / data-label`.
- **SHOULD:** 한 화면에서 실제 사용하는 크기와 굵기의 종류를 제한하고, 굵기·색상·크기를 모두 동시에 강조하지 않는다.
- **MUST:** 정보 위계가 단순한 글자 크기에만 의존하지 않도록 제목 구조와 의미론적 마크업도 적절히 사용한다.
- **매체 예외:** 인쇄물·발표 슬라이드의 글자 크기는 관람 거리·출력 크기·매체 특성에 맞춰 별도 규격을 만든다. 웹용 px 숫자를 그대로 강제하지 않는다.

### 4.3 색상과 대비

- **SHOULD:** 색은 취향뿐 아니라 **역할**을 기준으로 정한다: `surface / elevated-surface / text-primary / text-secondary / border / accent / success / warning / danger / focus`.
- **SHOULD:** 중립적인 바탕과 절제된 강조색은 하나의 출발점이며 모든 브랜드에 강제하지 않는다. 표현적 브랜드·웹툰·애니메이션·포트폴리오 등에서는 색·타이포그래피·시각적 리듬을 풍부하게 활용할 수 있다. 의미를 전달할 때는 색 외의 단서와 읽기 위계를 확보한다.
- **MUST:** 색만으로 필수 의미를 전달하지 않는다. 텍스트, 아이콘, 패턴, 형태, 위치 등 대체 단서를 제공한다.
- **WCAG 2.2 AA:** 일반 텍스트 대비 **4.5:1**, 큰 텍스트 대비 **3:1**을 검증한다. 필요한 인터페이스 경계·상태의 비텍스트 대비는 일반적으로 **3:1**을 검토한다(공식 예외·적용 범위 확인).
- **MUST:** 밝은 테마·어두운 테마를 지원한다면 기본·호버·포커스·오류·비활성 등 모든 상태를 각각 검증한다. 팔레트 예시만으로 접근성을 ‘통과’했다고 주장하지 않는다.

### 4.4 형태·표면·아이콘

- **SHOULD:** 모서리 반경과 그림자는 위계나 상호작용을 설명하기 위해 사용한다. 모든 컨테이너를 둥근 카드로 만들지 않는다.
- **SHOULD:** 아이콘은 이해를 빠르게 할 때만 사용하며, 모호한 아이콘에는 짧은 라벨을 붙인다.
- **SHOULD:** 버튼·입력·탭·필터·링크는 서로 다른 역할을 시각적으로 구분한다. 클릭 가능해 보이지만 동작하지 않는 가짜 조작부를 만들지 않는다.
- **MUST:** 이미지·도형·일러스트의 장식성이 사실성 또는 기능성을 과장하게 만들지 않는다.

### 4.5 이미지·그래픽·시각화

- **SHOULD:** 이미지마다 목적을 구분한다: 설명, 증거, 맥락, 감성, 탐색. 목적이 없는 장식 이미지는 제거 또는 축소를 고려한다.
- **MUST:** 이미지·도표의 출처, 저작권, 라이선스·사용 권한을 확인한다. 디자이너·브랜드의 작품을 **레퍼런스**로 삼는 것과 이미지를 **복제·재사용**하는 것은 다르다.
- **MUST:** 데이터 시각화에는 단위·범례·기간·출처·측정인지 추정인지 등을 필요한 만큼 표시한다. 축 절단, 색상, 크기 등으로 오해를 유도하지 않는다.
- **SHOULD:** 의미 있는 차트·이미지에는 대체 텍스트, 인접 설명, 필요한 경우 데이터 표를 제공한다.
- **콘텐츠 예시:** 논문 분석과 대중문화 콘텐츠를 연결하는 블로그라면 **연구 결과 / 연구자의 해석 / 필자의 비유·의견**을 제목·레이블·출처로 구분해 재미와 정확성을 함께 확보한다.

### 4.6 움직임과 미세 상호작용

- **SHOULD:** 애니메이션은 방향, 원인과 결과, 현재 상태, 진행 상황을 설명할 때 사용한다.
- **MUST:** 움직임만으로 정보를 전달하지 않는다. `prefers-reduced-motion`을 존중하며, 자동재생·반복 재생이 목적과 접근성을 해치지 않는지 확인한다.
- **MUST:** 시각적 연출 때문에 입력값·계산값·콘텐츠 상태가 의도치 않게 바뀌어서는 안 된다.

## 5. UI 패턴과 콘텐츠 구조

### 5.1 사이트·페이지 구조

- **랜딩 페이지:** 목적 또는 핵심 가치 → 가장 중요한 행동/콘텐츠 → 구체적 근거 → 보조 선택지.
- **블로그·에디토리얼:** 분명한 제목 → 요약/문제의식 → 본문 흐름 → 이미지·도표의 설명 → 출처/추가 읽기 → 탐색 연결.
- **대시보드:** 핵심 질문 또는 상태 → 중요한 지표 → 비교/원인 추적 → 상세 분석 → 필요 시 행동. 동시 비교가 핵심이면 관련 차트를 함께 배치한다.
- **웹앱·도구:** 현재 작업·상태 → 조작 가능한 요소 → 결과·피드백 → 취소·복구·도움말.
- **발표·문서:** 슬라이드/절당 하나의 주요 메시지 → 근거 → 해석 → 다음 메시지로의 연결. 청중의 거리와 읽기 시간을 고려한다.

위 순서는 권장 출발점이다. 복잡한 콘텐츠를 무조건 동일한 ‘5단계 화면’으로 쪼개라는 뜻은 아니다.

### 5.2 인터랙션의 필수 상태

상호작용이 있는 컴포넌트는 해당하는 상태를 설계한다.

| 상태 | 사용자에게 알려야 할 것 |
|---|---|
| Default / Hover / Focus / Active | 무엇을 조작할 수 있으며, 현재 무엇에 초점이 있는가 |
| Loading / Pending | 요청을 받았는가, 처리 중인가, 중복 실행해도 되는가 |
| Success / Updated | 실제로 무엇이 저장·적용·변경되었는가 |
| Empty / No results | 데이터가 없는 것인가, 필터 조건 때문인가, 다음에 무엇을 할 수 있는가 |
| Error / Invalid | 어떤 문제가 있었고, 사용자는 어떻게 복구할 수 있는가 |
| Disabled / Unavailable | 왜 이용할 수 없는가, 대안은 무엇인가 |

- **MUST:** 확인하지 않은 성공·저장·업로드 완료를 시각적으로 암시하지 않는다.
- **MUST:** 필수 작업은 키보드로 접근 가능하고 포커스가 보여야 한다. 모달·탭·내비게이션의 초점 이동·복귀를 점검한다.
- **SHOULD:** 선택·수정이 많은 화면은 *임시 변경(pending)*과 *확정된 변경(committed)*의 차이를 사용자에게 명확히 알린다.
- **SHOULD:** 한 작업 맥락에 주 행동을 분명하게 두되, 실제로 병렬 행동이 필요한 작업을 억지로 하나로 제한하지 않는다.

### 5.3 반응형·포용적 설계

- **MUST:** 너비가 좁아져도 필수 콘텐츠와 작업이 유지되어야 한다. 중요한 텍스트를 억지로 줄이지 않고 열 재배치·선택적 접기·일부 영역의 적절한 스크롤을 사용한다.
- **SHOULD:** 웹 화면은 320 / 360 / 390px, 태블릿, 데스크톱 등을 포함해 실제 콘텐츠와 조작 상태를 검증한다. 고정된 기기명보다 **깨지는 지점에 따른 반응형 설계**를 우선한다.
- **SHOULD:** 주요 터치 조작 영역은 가능하면 **44×44 CSS px**을 디자인 목표로 한다. 이는 본 문서의 여유 있는 선호 목표이며, **WCAG 2.2 AA에서 모든 대상에 44px을 의무화한 것은 아니다**. WCAG 2.2의 2.5.8(AA)은 **24×24 CSS px 또는 규정된 간격·동등한 기능 등 예외**를 포함한다. 실제 타깃 경계와 간격을 검증한다.
- **MUST — 텍스트 확대(WCAG 2.2 SC 1.4.4, AA):** 캡션·텍스트 이미지 등 공식 예외를 제외한 텍스트를 보조공학 없이 **200%까지 확대**해도 내용·기능이 손실되지 않는지 별도로 검증한다.
- **MUST — 리플로우(WCAG 2.2 SC 1.4.10, AA):** 세로로 읽는 웹 콘텐츠는 **320 CSS px 폭에 상당하는 조건**에서 정보·기능의 손실이나 불필요한 양방향 스크롤이 없는지 검증한다(예: 데스크톱 1280px에서 400% 줌). 표·지도·큰 그래프 등 본질적으로 2차원 배치가 필요한 콘텐츠는 해당 부분에 한하여 예외적 스크롤이 허용될 수 있다. 200% 확대 검사와 리플로우 검사는 서로 대체하지 않는다.
- **MUST:** 초점 표시와 읽기 순서가 논리적이어야 하며, 사용자가 선택한 움직임 감소 옵션과 접근성 환경에 적응해야 한다.


### 5.4 매체별 확장 지침 (권장 출발점)

범용 가이드는 모든 매체에 동일한 픽셀·문단·장면 구조를 강제하지 않는다. 세부 설계와 합격 기준은 각 매체의 목적과 사용 환경에 맞춰 작성한다.

| 매체 | 우선 확인할 사항 | 대표 검증 질문 |
|---|---|---|
| **블로그·에디토리얼** | 탐색 → 문제의식 → 근거·해석 구분 → 출처 → 관련 글; 이미지의 역할과 권리 | 독자는 '연구 결과'와 '필자의 해석'을 혼동하지 않는가? |
| **데이터·업무용 앱** | 정보 밀도, 다중 정보 비교, 오류 복구, 정렬·필터·저장 상태 | 조건을 바꾸어도 중요한 수치와 맥락을 놓치지 않는가? |
| **디지털 문서·보고서** | 제목 계층, 목차·탐색, 표·그림 캡션, 페이지 전환·인쇄, 출처 | 페이지를 넘어가도 논리 흐름과 참조 관계가 유지되는가? |
| **프레젠테이션** | 슬라이드당 주요 메시지, 투사/관람 거리, 제한된 읽기 시간, 발표 흐름, 도표·사진의 출처 | 뒤쪽 청중도 핵심 문장과 도표의 단위·범례를 읽을 수 있는가? |
| **정보 시각화** | 축·단위·기간·비교 기준, 상호작용·범례·대체 설명 | 시각 표현이 실제 데이터 이상의 확실성을 암시하지 않는가? |

- **SHOULD — 문서:** 인쇄·PDF·전자문서 출력 시 표의 잘림, 페이지 번호, 머리글/바닥글, 링크 및 목차 탐색 가능 여부를 확인한다.
- **SHOULD — 발표:** 100% 화면 미리보기뿐 아니라 실제 또는 근사한 관람 거리에서도 확인하고, 대화면에서 읽기 어려운 텍스트를 한 슬라이드에 과도하게 넣지 않는다. 숫자형 글자 크기 하나로 모든 발표를 규정하지 않는다.
- **MUST — 출처:** 연구·인용·시각자료를 사용하는 매체에서는 출처와 사실·해석 구분을 유지한다. 구체적인 연구 해석·서지 메타데이터·DOI 검증은 해당 콘텐츠 전문 지침에서 다룬다.

## 6. 반복 가능한 디자인 토큰과 컴포넌트

**SHOULD:** 제품 내 공통 언어를 아래처럼 역할 중심으로 정의한다. 숫자·색상값은 **프로젝트별로 정하는 것**이며, 본 가이드는 단일 강제 팔레트를 지정하지 않는다.

```text
Color       color.surface / color.text.primary / color.text.secondary
            color.border / color.accent / color.success / color.warning / color.danger
Typography  type.display / type.h1 / type.h2 / type.body / type.caption / type.data
Spacing     space.1 / space.2 / space.3 / space.4 / space.6 / space.8 ...
Shape       radius.none / radius.sm / radius.md / radius.lg
Depth       shadow.none / shadow.surface / shadow.overlay
Interaction state.default / state.hover / state.focus / state.pending / state.error
Motion      motion.fast / motion.normal / motion.reduced
```

**권장 기본 컴포넌트:** 버튼, 링크, 입력, 셀렉트, 검색, 카드/섹션, 탭, 표, 상태 메시지, 모달/대화상자, 도움말, 차트 설명, 빈 상태. 필요하지 않은 컴포넌트를 억지로 도입할 필요는 없다.

- 같은 역할을 가진 구성 요소에는 같은 토큰과 상태 규칙을 사용한다.
- 장식적 스타일보다 크기·여백·타이포그래피·상태·접근성의 재사용을 우선한다.
- 코드화된 UI라면 실제 값과 렌더링 결과의 차이를 검증한다. 디자인 시안 자체는 구현 및 접근성 통과를 뜻하지 않는다.

## 7. 실제 프로젝트에 적용하는 절차

1. **맥락 확인:** 대상 사용자, 주요 콘텐츠/작업, 성공 조건, 매체와 기기, 브랜드, 유지해야 할 요소를 정의한다.
2. **현황 진단:** 기존 화면·문서의 첫인상, 읽기 흐름, 반복 요소, 경쟁하는 강조, 접근성·상태·유지보수 위험을 확인한다.
3. **레퍼런스 선택:** Rams/Braun, ChatGPT, Apple, Carbon 등에서 **해결하려는 문제와 맞는 한두 가지 패턴**을 고르고, 적용 이유를 적는다.
4. **와이어프레임:** 색상·장식을 만들기 전에 정보 위계, 콘텐츠 순서, 그리드, 공백, 핵심 행동을 정한다.
5. **시각 언어 설정:** 타입·여백·색상 역할·형태·반응형 규칙·상태를 토큰과 컴포넌트로 구체화한다.
6. **변경 위험 평가:** 화면·데이터·기능·접근성·핵심 상태에 미치는 영향을 분류하고 **7.1의 위험도에 맞춰** 구현·테스트 범위를 정한다. 여러 작은 변경이 누적되면 위험도를 다시 산정한다.
7. **작은 범위로 적용:** 기존 구조가 있다면 영향과 되돌릴 방법을 검토하고, 가능한 한 작은 영역부터 구현한다. 데이터·기능·저장/복원·내비게이션을 임의로 바꾸지 않는다. 저장 구조가 바뀌면 **7.2의 호환성 절차**를 적용한다.
8. **기술 검증:** 가독성·대비·키보드·포커스·확대·리플로우·반응형·모션 감소·오류 상태와 영향을 받는 기존 기능을 확인한다. 실제 검사 항목과 합격 기준은 **7.3의 검증 계약**으로 정한다.
9. **사용자 검증:** 필요성과 위험도에 따라 실제 이용자에게 화면의 목적을 설명하게 하고 대표 작업·읽기 과제를 수행하도록 하여 혼란·오류·재탐색·이해도를 평가한다. 수행하지 못했다면 미검증으로 기록한다.
10. **기록·개선:** 선택한 레퍼런스, 채택한 원칙, 달라진 점, 검증 범위·실행 환경·결과, 미검증 사항, 후속 개선점을 문서화한다.

**의사결정 분담:** 국소적인 정렬·반응형·토큰 구현 등 기술적 판단은 프로젝트의 위임 범위에서 처리할 수 있다. 정보 구조 변경, 브랜드 정체성 변경, 주요 콘텐츠 제거, 핵심 기능 이동, 기존 데이터/사용자 작업의 손실 가능성이 있는 변경은 **대안·장단점·복구 경로**를 제시하고 승인받는다.

### 7.1 변경 위험도별 검토 및 검증 수준

아래는 **검증 범위를 정하는 실무 기본값**이다. 접근성·사실성·안전·기존 계약의 MUST를 면제하지 않는다. 가장 위험한 영향 영역을 기준으로 분류하며 프로젝트별 위험 분류가 더 엄격하면 해당 기준을 따른다.

| 등급 | 해당 변경의 예 | 구현 전 검토 | 최소 검증 범위 |
|---|---|---|---|
| **L — 낮음** | 영향이 국소적인 여백·정렬·장식 변경, 문구 오탈자 수정 | 해당 화면·컴포넌트와 인접 영역 확인 | 변경 화면에서 시각 확인, 대표 반응형 폭·포커스·가독성 등 관련 항목 점검 |
| **M — 중간** | 검색·필터·폼 동작, 컴포넌트 교체, 화면 간 탐색 변경 | 연결 상태, 사용자 흐름, 영향받는 기존 기능 확인 | 변경 기능의 정상·실패·빈 상태, 키보드, 모바일, 저장/복원 등 관련 회귀 테스트 |
| **H — 높음** | 데이터 저장 키·스키마·계정·동기화·삭제 흐름 변경, 핵심 상태 변경, 안전 정보·핵심 모델 관련 변경 | 데이터 보존·역호환·복구, 의존 기능, 필요 시 도메인별 검토와 승인 | 구버전 실데이터/픽스처 이전·실패/롤백·재방문, 영향 범위 회귀, 접근성·예외 상태·안전 요건 검증 |

- **MUST:** 위험을 낮게 분류했다는 이유로 변경으로 영향받는 필수 기능의 실패를 무시하지 않는다. 테스트 범위는 영향 분석으로 선택하며, 작은 CSS 수정도 포커스 가림이나 텍스트 손실을 일으킨다면 관련 접근성 검사가 필요하다.
- **SHOULD:** 자동 테스트가 없는 초기 프로토타입은 수동 점검을 기록할 수 있지만, 실제로 실행하지 않은 테스트를 PASS로 표기하지 않는다.
- **SHOULD:** 동일 기능의 패치가 누적되어 구조·스타일 충돌이 우려되면 유지보수성과 리팩터링 필요성을 재평가한다.

### 7.2 기존 데이터·상태·버전 호환성

**MUST:** 기존 기능이나 저장 구조를 변경할 때는 이전 버전과의 호환성을 검토한다. 데이터 스키마·저장 키·상태 구조·URL·내비게이션 계약이 바뀌는 경우 **마이그레이션, 구버전 읽기 호환 또는 명시적 데이터 이전 방식**, 실패 시 복구·롤백 방안을 정의한다. 사용자의 콘텐츠와 북마크가 단지 새 버전에서 **보이지 않게 된 것**도 데이터 접근성의 회귀로 취급한다.

**MUST:** 변경 후에는 새 데이터뿐 아니라 **구버전의 실제 데이터 구조를 대표하는 픽스처** 또는 적법하게 확보한 테스트 데이터를 사용하여 이전·새로고침·재방문·버전 전환을 검증한다. 개인정보·민감정보를 테스트 기록이나 저장소에 복사하지 않는다.

**MUST:** 사용자 데이터를 삭제하거나 자동 변환할 경우, 되돌릴 수 없는 변경과 손실 위험을 사전에 식별하고 승인된 제품 정책에 따라 처리한다. 실패·부분 이전 시 저장된 데이터와 사용자 안내가 어떻게 되는지 검증한다.

**SHOULD:** 호환성 확인표에 ① 이전 버전/키·스키마 ② 새 버전/키·스키마 ③ 이전·재시도 전략 ④ 충돌·중복 처리 ⑤ 복구 방법 ⑥ 테스트 결과를 남긴다. 신규 프로젝트처럼 **보존할 기존 데이터가 없다면 해당 사항 없음(N/A)**으로 기록한다.

**예시 — 로컬 블로그:** v0.1에서 저장한 사용자 작성 글과 북마크를 v0.2에서 읽을 수 없다면, 브라우저 저장소의 원본이 남아 있어도 '기존 데이터 보존' 검증은 통과하지 못한다. 이전 로직이나 읽기 호환 계층 및 실제 구버전 픽스처 테스트가 필요하다.

### 7.3 검증 계약과 증거 보고

구현 전에 **대상·시나리오·기대 결과·실행 환경·담당 검증 방식**을 최소한으로 정한다. 합격 기준은 프로젝트별로 수립하며, 예시 수치(예: 첫 화면 5~10초 내 목적 설명)를 보편적 준수 조건으로 단정하지 않는다.

| 구분 | 증거의 예 | 보고 규칙 |
|---|---|---|
| **문서/코드 검토** | 설계 문서와 코드의 요구사항 대조, 정적 분석 | 설계상 부합 여부만 말한다. 렌더링·실사용 PASS가 아님 |
| **자동 실행 테스트** | 테스트 스크립트·픽스처·실행 결과 | 실행 환경·검증 범위·실패 항목을 명시한다 |
| **브라우저/기기 수동 점검** | 실제 화면 크기·입력·포커스·저장/복원 조작 기록 | 검사한 브라우저·기기·뷰포트만 밝힌다 |
| **사용자 사용성 검증** | 참여자·과제·성공/오류·관찰 기록 | 적절한 이용자를 대상으로 수행한 경우에만 사용성 개선을 주장한다 |
| **전문가 검토** | 임상·법률·과학·접근성 분야의 명시적 검토 | 관련 전문 검토 사실과 범위를 확인한 경우에만 승인으로 표현한다 |

**MUST:** 검사 상태를 **PASS / FAIL / NOT RUN / N/A**로 구분한다. 미실행을 통과로 처리하지 않으며, FAIL이 남은 경우 영향과 배포 판단을 명시한다. 성공 메시지는 저장·반영을 실제로 확인한 뒤 표시한다.

**SHOULD:** 사례별 검증 시나리오를 정의한다. 예를 들어 블로그에서는 제목·본문 검색, 본문 읽기, 작성 → 저장 → 새로고침 → 재진입, 구버전 데이터 이전, 키보드 접근, 확대·리플로우 등이 대표 시나리오다. 작업 특성상 해당 없는 항목을 무조건 수행하지 않는다.

## 8. 디자인 리뷰 체크리스트

아래 질문 중 해당 항목에 답할 수 있어야 한다.

### 목적·콘텐츠
- [ ] 처음 보는 사람이 5~10초 안에 화면/문서의 용도를 설명할 수 있는가? (검증을 위한 권장 질문, 보편적 합격 기준은 아님)
- [ ] 가장 중요한 정보 또는 행동이 분명한가?
- [ ] 정보의 누락, 과장, 출처 불명, 사실/의견 혼동이 없는가?

### 시각적 완성도
- [ ] 프로젝트의 브랜드·문화·콘텐츠 정체성을 살리면서 핵심 정보의 가독성을 유지하는가?
- [ ] 제목·본문·보조 설명의 위계가 명확한가?
- [ ] 그리드·여백·간격·비례가 일관적인가?
- [ ] 강조색과 아이콘에는 각각 이유가 있는가?
- [ ] 카드·구분선·그림자·움직임이 과도하지 않은가?
- [ ] 정보가 많더라도 비교·해석이 가능한가?

### 인터랙션·접근성
- [ ] 조작 가능 여부와 현재 상태가 명확한가?
- [ ] 오류·저장·로딩·빈 상태에서 다음 행동을 알 수 있는가?
- [ ] 대비, 키보드, 포커스, 모바일, 움직임 감소를 확인했는가?
- [ ] 텍스트 200% 확대(SC 1.4.4)와 320 CSS px 상당 조건의 리플로우(SC 1.4.10)를 **별도로** 확인했는가?
- [ ] 한국어/영문 혼합 콘텐츠와 긴 링크·DOI 등의 줄바꿈을 확인했는가?
- [ ] 색상이나 애니메이션 하나에만 의미를 의존하지 않는가?

### 구현·검증
- [ ] 변경 위험도(L/M/H)와 그에 따른 영향받는 기능의 테스트 범위를 정했는가?
- [ ] 변경으로 기존 기능·데이터·저장 상태가 손상되지 않는가?
- [ ] 구버전 데이터·북마크·URL·상태의 호환성, 마이그레이션 및 롤백을 검증했는가(해당 없으면 N/A)?
- [ ] 결과를 PASS/FAIL/NOT RUN/N/A로 기록하고 근거 환경을 남겼는가?
- [ ] 실제 브라우저·기기·사용자 테스트와 문서상 검토를 구분했는가?
- [ ] 다른 제품에서 무엇을 참고했고 왜 적용했는지 설명할 수 있는가?

## 9. 적용 범위와 권한

1. 이 가이드는 **범용 시각 디자인 및 UI/UX 결정의 출발점**이며, 어느 프로젝트의 기존 디자인·컴포넌트·코드를 자동으로 대체하지 않는다.
2. 기존 승인된 프로젝트 계약, 법적·의료적 안전 요구, 브랜드 지침, 기술 제약이 충돌하면 **관련 프로젝트의 더 구체적이고 유효한 요구사항**을 우선하고 차이를 보고한다.
3. 시뮬레이터 전용 모델·상태·교육 흐름·버전 제약은 별도 `Simulator_Project_Design_Constraints_v1.0.md`로 분리한다. 원본 `Educational Simulator UI/UX Design Standard v1.0`은 변경 이력과 계약 확인을 위해 보존한다.
4. 문서 작성만으로 구현, 회귀 테스트, 사용성 조사, 접근성 인증 또는 전문가 검토가 완료된 것으로 간주하지 않는다. 또한 디자인의 표현적 정체성 보강은 승인된 브랜드 및 콘텐츠 전략을 임의로 교체할 권한을 부여하지 않는다.
5. 이 가이드 자체를 바꿀 때는 변경 이유, 예상 영향, 기존 작업물과의 충돌 가능성을 검토해 버전을 갱신한다.
