# PRN Order Viewer v0.4 — 모듈형 사이드바 및 처방 변경 이력

작성일: 2026-10-10 · 독립형 교육·시연용 · nU/병원 EMR 아님

## 1. 사용자 제안에 대한 검토

현재 프로그램은 PRN 조회에서 시작해 가상의사 입력, 환자상황, Kardex 인계, MICU 근무표까지 패널을 추가해왔다. 이를 하나의 스크롤 화면에 계속 누적하면:
- 필요한 처방 탐색에 긴 스크롤·시각적 혼잡이 생긴다.
- 데이터 관리·조회·작성 화면의 업무 맥락이 섞인다.
- 세 프로젝트를 앞으로 통합할 때 UI 모듈의 경계가 불명확해진다.

### 선택한 방식
- **하나의 웹앱, 왼쪽 사이드바, 각 업무를 독립 화면으로 전환**.
- 실제 새 브라우저 창/탭을 여는 방식이 아님. 공통 가상 환자 선택과 화면 상태를 유지한 채 중앙 작업 영역을 바꾼다.
- UI만 재구성하고 기존 코드·가상 환자·약물 마스터·MICU 백업 규칙은 삭제하거나 변경하지 않는다.
- 화면은 임시 UX이며 향후 쉽게 교체할 수 있도록 선택 화면 전환은 `workspace-nav.js`, 가상 처방 이력은 `order-history-model.js`로 분리한다.

### 사이드바 6개 메뉴

| 메뉴 | 관리 대상 | 기존 컴포넌트 |
|---|---|---|
| 약물 처방 조회 (기본 진입) | 전체/PRN, 검색·상태, 상세, 간호사 열람확인 | `orders-panel`, `detail-panel`, `session-bar` |
| 환자 정보 | 가상 병력·현재 상태 | `patient-summary` |
| 인계·Kardex | 교내 워크리스트 참고, 인계, Order Manage 형식 조회 | `sheet-panel` |
| 의사 처방 입력 | 가상 약물 정규/PRN/응급 입력 | `composer-panel` |
| 처방 변경 이력 | 가상 의사 변경·보류·재개·중지(D/C)·취소와 이력 | `history-panel` |
| MICU 근무표 | 전체 백업 읽기 전용 조회 | `roster-bridge-panel` |

공통 선택 환자만 상단에서 유지. 메뉴 전환은 URL/저장소/진료정보를 바꾸지 않는다. 좁은 화면에서는 왼쪽 메뉴가 상단 가로 스크롤 메뉴로 변형된다.

## 2. 다음 단계 동시 구현: 약물 처방 이벤트 모델

`order-history-model.js`는 순수 함수로 별도 처방 이벤트를 만든다. 사용자가 조작하는 처방 이벤트는 `data/verification_events.json`의 **간호사 열람 확인 이력과 별개의 배열**이다.

### 이벤트 동작

| 이벤트 | 허용되는 현재 상태 | 다음 상태/효과 |
|---|---|---|
| 추가(add) | 새 가상 처방 | 원본 변경 없이 메모리 처방 추가 |
| 변경(revise) | active/on-hold | 입력한 1회 용량·경로·빈도 중 바뀐 항목을 갱신 |
| 보류(hold) | active | on-hold |
| 재개(resume) | on-hold | active |
| 중지(stop) | active/on-hold | stopped (D/C 시뮬레이션) |
| 취소(cancel) | active/on-hold | cancelled |

완료·중지·취소 처방의 재개 및 수정은 거부한다. 수정 전·후 스냅샷, 가상의사 ID/표시명, 시각, 사유, 처방·환자 ID, 버전을 이벤트로 보존한다. 수정한 처방은 동일 `order_id`의 최신 **표시 스냅샷**으로 갱신되며 기존 기본 JSON은 그대로다.

### 중요한 구분
- **처방 변경 이력:** `orderEvents` 메모리 배열. 의사 시뮬레이션 이벤트, 브라우저 탭 종료 시 소실.
- **처방 열람 확인 이력:** `reviews`. 간호사 모의 로그인 세션의 클릭 행동에만 생성되는 다른 종류의 기록.
- 처방이 바뀌면 `order_revision`이 증가한다. **이전 버전을 확인한 간호사 이력은 현재 버전의 확인으로 취급하지 않는다.** 목록의 최근 확인자와 상세의 현 버전 확인 기준을 분리한다.
- 갱신 시점보다 이른 간호사 모의 근무시간으로 새 버전을 확인할 수 없다.
- 기존 가상 PRN에 미기재인 투여 조건은 수정 과정에서 임의로 채우지 않는다. PRN 조건 자체를 변경할 경우 적응증/조건 양쪽의 존재를 요구한다.
- 의사 입력을 통한 **새** PRN 처방은 기존대로 적응증과 투여 조건 필수.
- 실제 처방·서명·취소·투약권한·의료기관 감사 추적기록이 아니다.

## 3. 통합 준비와 저장 정책

세 프로젝트를 즉시 합치지 않음:
- MICU: `roster-bridge.js`의 파일 기반 읽기 전용 조회 유지. 원 프로그램 IndexedDB나 배치 기능 불변.
- 간호처방 개선: 별도 저장소, ACT/FOLLOW/MAT 분류 유지. 환자 ID·related_request_id는 장기 참조 계약으로만 계획.
- PRN: 기존 환자 4명, 약물 107개, 기본 약물 처방 18건, 간호사 기본 확인 3건 변경 없음.

**새로 작성한 약물 처방과 변경 이력 모두 현재 탭 메모리에만 존재한다.** localStorage/IndexedDB/백엔드 저장을 임의로 추가하지 않는다. 다음 영속화 설계에서는 복구, 초기화, 폐기 정책 및 임상 자료 사용 금지를 사전 합의한다.

## 4. 검증

- 기존 핵심 14건, 의사 처방 8건, 워크리스트·처방지 모델 7건, 이력 9건, 사이드바 구조 4건 = **42/42 통과**.
- GitHub `main`의 코드와 테스트 내용을 독립 JavaScript 실행 환경에서 평가한 결과. **실제 Codespaces Node.js 명령과 브라우저 통합·시각 검수는 미실시**.
- 화면 구조는 정적 구조·이벤트 핸들러 범위 검증만 완료. 실제 반응형 레이아웃, 클릭 조작, 정보 밀도 판단은 사용자 요청에 따라 최종 MVP 때 실시.
- MICU 브리지 통합 테스트는 이번 변경 범위에서 다시 수행하지 않았으며, 해당 파일은 수정하지 않음.

## 5. 다음 단계 제안

1. 각 화면 내 실제 업무 동선 검토: 처방 조회에서 이력 확인, 환자 전환, 의사 입력 후 조회 복귀.
2. 비약물 처방(검사·드레싱·간호수행) 데이터의 **도메인별 분리와 참조 ID 설계**. SST/EDTA는 채혈관이며 검사명과 분리할 것.
3. 임시 기록의 선택적 저장/초기화 정책을 사용자와 협의한 후 테스트용 지속 저장을 구현.
4. 세 프로젝트 공통 식별자 교환 방식만 점진적으로 도입; 저장소/DB 대규모 병합은 MVP 안정화 이후 판단.
5. v1.0 통합 MVP 단계에서 실제 시각 검수와 수동 테스트, 접근성·회귀검증 수행.
