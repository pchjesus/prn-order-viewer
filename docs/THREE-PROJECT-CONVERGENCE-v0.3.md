# PRN Order Viewer v0.3 — 가상 의사 약물 처방 입력 및 통합 준비

작성일 2026-10-10 · 비공개 독립형 시뮬레이션 · 실제 EMR·nU 연동 아님

## 1. 목적

기존 환자별 PRN/정규 약물 처방 조회 화면을 그대로 유지하면서 **가상의사가 처방을 입력하면 간호사 화면에 즉시 나타나는 작업 흐름**을 시험한다.
현재 앱에는 실제 인증, 전자의무기록 서버, 임상 용량/상호작용 검증 및 투약 승인 기능이 전혀 없다.

## 2. 현재 구현

- 같은 가상 환자 4명과 기존 약물 마스터 107종을 참조한다.
- 의사 입력 화면은 접기/펼치기 가능하며 기존 UI 배치는 향후 언제든 개편할 수 있다.
- 가상 처방의사와 약물 성분을 선택한다.
- 1회 용량·단위, 투여 경로, 빈도·간격, 모의 처방 시각 입력은 필수.
- PRN은 적응증과 구체적 PRN 투여 조건까지 필수.
- 정규 / PRN / 응급(STAT) 세 형태를 선택한다. 응급(STAT)은 **우선순위**이며 정규/PRN은 **투여 방식**이다. 이번 UI에서 응급 선택은 `order_type=regular`, `order_mode=emergency`, `order_priority=stat`으로 모델링해 PRN과 혼동하지 않는다. 미래에는 PRN+긴급도 조합을 별도로 지원할 수 있다.
- 가상 약물처방 1건 생성 시 고유 `SIM-ORD-NEW-...` ID를 부여하고 기존 환자의 전체/PRN 목록·상세·검색에 자동 반영.
- 등록한 데이터는 **현재 브라우저 탭 메모리**에만 저장. 새로고침 후 소실되므로 실제 보존·감사 기록이 아니다.
- 등록된 처방은 `simulated_input=true`, `is_clinically_complete=false`, `dose_review_status=simulation_unverified`. 어떤 값도 실제 환자에게 투여해도 된다는 보장이 없다.
- `order-composer.js`의 순수 함수와 `doctor-ui.js` 화면 어댑터를 분리해 향후 UI 교체 시 데이터/규칙을 재사용한다.

## 3. 도메인 간 관계 (장기 통합을 위한 계약 초안)

| 도메인 | 필수 개념 | 고유 ID/참조 | 현재 구현 |
|---|---|---|---|
| 환자 | Patient | `patient_id` | PRN 가상 환자 4명 |
| 직원 | Staff / Prescriber / Nurse | `staff_id`, 기존 `SIM-MD-...`, `SIM-RN-...` 매핑 | 기존 가상 ID 유지 |
| 근무표 | Roster/Shift | 근무표 ID·근무조·직원 ID | MICU 독립; 일방향 임시 브리지 |
| 의사 처방 | Order Envelope | `request_id`, `patient_id`, `domain`, `mode`, `priority` | `createEnvelope()`로 초안 |
| 약물 처방 | MedicationOrder | `medication_order_id` → Order Envelope | 이번 버전은 약물만 생성 |
| 검사 의뢰 | ServiceRequest | `service_request_id`, 검사코드, 검체 ID | 향후 |
| 드레싱 등 처치 | Procedure/ServiceRequest | 처치 종류·부위·반복 주기 | 향후 |
| 간호 행위 | NursingActivity/Task | `activity_id`, `related_request_id` | 간호처방 프로젝트 영역 |
| 소모품·용기 | Material/Device | `material_id`, `related_request_id` | 처방과 분리 |

**검사명과 검체 용기를 구별한다.** 예: 객담 배양은 검사 의뢰의 예시, SST·EDTA는 채혈관/검체 용기 분류에 해당한다. 향후 검사 처방 폼에는 검사명·검체 종류·채취 용기(SST/EDTA 등)·채취 방법·의뢰 목적을 각각 관리한다. 지금은 개별 검사 목록이나 검사 채혈관 관련 처방을 추가하지 않는다.

**실제 nU/병원 내부 코드 체계와 호환된다고 주장하지 않는다.** FHIR 자원(예: MedicationRequest, ServiceRequest)의 개념적인 분리를 참고할 수 있으나 현재 앱이 FHIR 적합성을 달성한 것은 아니다.

## 4. 다른 두 프로젝트와 합칠 때 지켜야 할 경계

### MICU 화재대피 앱 (현재 v0.7.4 RC)

- 현행 `fireEvacuationRosterDB_v0617` IndexedDB 데이터·근무표 저장, 수정이력, 자동 인원배치, 백업/복원을 **절대 직접 변경하지 않음**.
- 향후 공통 가상 직원 ID·최소 근무 정보 JSON 교환만 검토. 현재 근무표에 이름이 존재한다는 이유로 로그인 및 처방 확인을 자동 처리하지 않음.
- MICU는 환자 관리 기능이 현재 없으므로 환자 데이터의 동기화나 복제를 강제하지 않음.
- 새로운 시스템 간 자동 동기화나 API 통합은 사용자 승인, 개인정보·인증·충돌정책이 정해진 다음에만 검토.

### 간호처방 개선 앱 (현재 v0.2.1 MVP)

- 기존 `ACT`(간호행위), `FOLLOW`(처방 연계 수행), `MAT`(소모품)를 구별하는 설계를 유지. 모든 항목을 의사 처방으로 재분류하거나 약물 처방과 동등한 객체로 합치지 않음.
- 장기적으로 `Patient` 공통 가상 ID·`related_request_id` 참조를 지원할 여지만 두고, 현재 315개 가상 후보와 24개 카테고리 및 UI 작동은 보호.
- 실제 임상 수행 권한/기록 규칙, 기관 내부 분류, 원본 데이터 병합은 검증과 승인 전 보류.

## 5. 구현 전·후 테스트 조건

- 기존 `app.js`의 기본 탭 전체약물, PRN 필터, active 우선 정렬, 기존 환자·처방·확인 기록과 MICU 백업 프리뷰 동작 보존.
- 새 의사 처방 입력: 유효한 가상 입력→해당 환자 목록 표시→기존 환자 목록 불변.
- PRN 입력에 적응증/조건 누락 시 거절.
- 응급(STAT)은 PRN 탭에 자동 편입되지 않음.
- 새로운 ID 충돌 금지, 다른 환자에 잘못 연결된 처방 거절, 환자/의사/약물 ID 무효 시 거절.
- 가상 용량·경로·시간 자동 추천 없음. 처방 생성 이후 실제 의사 서명·처방 승인·투약 가능성 평가 없음.
- 사용자가 허용하기 전까지 LocalStorage/IndexedDB 저장·API 전송 도입하지 않음.
- MVP 시각 검수는 사용자의 이전 결정에 따라 후속 시점까지 보류한다.

## 6. 앞으로 필요한 결정

1. 의사 작성·변경·취소 처방 이력의 저장·복원 범위: 임시 메모리 vs 브라우저 로컬 vs 서버/계정 동기화.
2. 약물 이외의 처방 영역을 어디까지 도입할지: 드레싱/처치·검사·검체·재료를 동일 탭에 보여줄지 별도 모듈로 관리할지.
3. 실제 임상 정보와 차이가 있는 가상 용량·조건을 어떻게 눈에 띄게 표시할지.
4. 다른 두 프로젝트의 데이터 교환 최소 규격과 공통 직원·환자 ID를 만들 시점.
5. 향후 통합 앱의 UI/UX·권한·데이터 삭제 정책은 사용자 최종 승인 후 확정.

## 8. 2026-10-10 후속 결정: PRN 우선 범위 및 통합 원칙 재확인

- 사용자와 논의하여 **PRN 확인에 직접 도움이 되는 기능만 당분간 우선 개발**하기로 결정했다. PRN 전용 목록/확인 버튼의 임상적 효과가 이미 입증되었다고 주장하지 않는다.
- 현재 범위는 환자별 PRN 처방 탐색, 적응증·투여 조건/용량·경로·빈도 확인, 처방 변경·보류·중지/버전 구별 및 가상 시나리오의 사용성 평가로 제한한다.
- 장기적으로 환자 중심 업무 환경을 지향한다. PRN 저장소를 통합 프로젝트의 개발 출발점으로 삼는 것과 모든 임상 도메인을 PRN 구조 아래 편입하는 것은 별개다.
- 간호처방 프로젝트와의 연계는 필요성 확인 후 검토하며, MICU 화재대피 앱은 직원/근무 관련 최소 연동 필요가 있는 경우에만 별도로 다룬다.
- 기타 통합 및 새로운 저장·삭제 정책은 **이번 결정에 포함되지 않았으며**, 별도 승인 전에는 구현하지 않는다.
- 현재 PRN 우선순위와 검증 계획의 정본: `docs/PRN-CLINICAL-UTILITY-AND-ROADMAP-v0.5.md`. 이 문서의 과거 시점 통합 구상과 해석이 충돌하면 최신 합의된 개발 범위를 우선한다.
